# next-save 도메인 원장 (저맥락판)

> **이 문서는 저맥락(low-context)으로 쓴다** — 세션 히스토리를 모르는 사람(서브에이전트·design·미래의 우리)이 이 문서만 읽고 일할 수 있게. 섹션 단위로 잘라 브리프에 붙여 넣을 수 있다.
> 제품 한 줄: **NEXT SAVE = Steam 플레이 이력을 "취향 아틀라스"(장르 대륙 지도 + 게이머 아키타입)로 보여주고, 그 지도에서 다음에 할 게임을 근거와 함께 추천하는 서비스.** 지금 단계 = v0 정적 데모 랜딩 한 장 (가입·백엔드·실연동 없음, 전부 예시 데이터 + "예시/데모" 표식).
> 볼륨 큐·태스크 상태 = `NEXT.md` (휘발). 이 문서 = 도메인의 정의·결정 대기 목록 (반휘발 — 결정이 나면 갱신).

---

## 커널 (내부 엔진 — 화면 없음)

### SIG — 신호 엔진
- **정의:** 플레이 기록(플레이타임·도전과제 달성)에서 취향 신호 S1~S4를 뽑아 유저의 코어(아키타입)를 판정하는 내부 로직. 화면은 없고, 지도 채색·아키타입 판정·추천 근거가 전부 이 엔진의 출력을 소비한다.
- **PRD 근거:** PRD v0.5 부록 A(데이터 신호) · 내부 분류 레이어(행동 페르소나 5종 — 표면 노출 없음).
- **정해야 할 것:**
  1. 헌신형 코어의 신호 귀속 — S1인가 S3인가 (현재 문서 간 불일치). → 태스크 M1
  2. 코어 개수 — 경쟁형과 협동소셜형이 신호로 갈라지는가 (5종 vs 6종). → 태스크 M1
  3. 신호 분리도·재현성 판정 기준 — 공개 Steam 프로필 5~8개 실측으로 확인. → 태스크 M1
  4. 장르별로 어느 코어에 신호를 주는지 매핑표 + "경쟁 장르 태그"의 정의. → 태스크 M2

### ARC — 아키타입
- **정의:** 유저의 게이머 정체성 표현 체계. 확정된 방향(2026-07-20 결정 A) = 하나로 딱 떨어지는 격자 판정이 아니라 **"소프트 코어" 5종** — 주 코어 + 강도% + 보조 태그 + 개인 근거 문장의 조합.
- **PRD 근거:** spec 001 FR-005(판정 표시) · FR-012(4분면 동등 톤). ⚠️ spec 문구는 아직 옛 체계("2축 4종")라 갱신 대기.
- **정해야 할 것:**
  1. 랜딩 표면에서의 거취 — design 최신안(v0.7)은 판정 표시를 삭제했다. 소프트 코어로 복원할지, 어떤 수위로 보여줄지. → 태스크 X1 [최우선]
  2. 소프트 코어의 표시 형식 — 코어+강도%+보조태그+개인근거를 화면에서 어떻게 배치할지. `[미채움]` — X1 합의에서 결정.
  3. 코어 명명 — 카토그래피(지도학) 레지스터 확정, 개별 이름은 미정(임시명 "산책자" 등). 플레이어 타이폴로지 연구·실서비스 사례 조사 후 확정. → 태스크 M4
  4. spec FR-004/005 문구 갱신. → 태스크 G1 (X1 결과 대기)

## 표면 (v0 랜딩에서 실제로 보이는 것)

### MAP — 아틀라스 지도
- **정의:** 12개 게임 장르를 대륙으로 그린 지도. 유저의 플레이타임에 따라 각 대륙을 미개척/탐험중/정복 3단계로 채색한다. 랜딩의 IDENTITY 블록 중심 요소.
- **PRD 근거:** FR-004(지도·채색) · FR-007/008(신호 접지 추천, 억지 추천 금지).
- **정해야 할 것:**
  1. design이 독자 추가한 "트렌드 게임 섹션"의 수용 여부 — 5블록 구조 밖의 추가다. → 태스크 X6
  2. 장르×코어 매핑표 확정(어떤 대륙이 어떤 코어의 영토인가). → 태스크 M2 결과 수용

### PIC — NEXT PICKS
- **정의:** 지도에서 도출된 "다음에 할 게임" 추천 카드 2~3장. 카드 = 게임명 + 신호에 근거한 "왜" 한 줄 + 클리어 소요시간. 데모 프로필을 바꾸면 카드도 함께 바뀐다.
- **PRD 근거:** FR-014.
- **정해야 할 것:**
  1. 별도 블록으로 둘지, design안(지도에 흡수)을 받을지. → 태스크 X2

### LND — 랜딩 프레임
- **정의:** 랜딩 페이지의 뼈대 — 히어로 헤드라인, "어떻게 작동하나" 3단계 설명, 데모 프로필 전환 장치, 5블록 순서(HERO → HOW IT WORKS → IDENTITY → NEXT PICKS → COMMUNITY).
- **PRD 근거:** FR-001(5블록) · FR-011(히어로) · FR-015(HOW IT WORKS) · FR-002/003(예시 표식·정적).
- **정해야 할 것:**
  1. 히어로 헤드라인의 무게추 — "게이머 정체성" 서사 우선인가 "백로그 정리 유틸" 우선인가 (기본값 = 유틸 우선). design과 재협의로 확정. → 태스크 X4
  2. 2번째 데모 프로필의 데이터셋 — 현재 design은 1개(@frost_warden)만 구현. → 태스크 X3

### GME — 게임 프로필
- **정의:** **게임 하나를 클릭했을 때 보이는 그 게임의 프로필.** v0에서 두 형태 — ① 지도/추천 카드 클릭 시 모달(추천 이유 "왜" + 클리어 소요시간 + 진행 CTA), ② 커뮤니티 블록에 임베드되는 게임 페이지(평균 플레이시간 · 글로벌 완주율 · 대표 도전과제 달성률의 3지표 + 접힌 별점/리뷰 보조 영역). 예시 게임 1종은 추천 동선과 연결(추천받은 게임 → 그 게임의 페이지).
- **PRD 근거:** FR-006(모달) · FR-009(게임 페이지 임베드) · FR-010(숫자 우선, 의견은 접힌 레이어) · game≠player 가드(게임 통계와 유저 기록을 섞지 않음).
- **정해야 할 것:**
  1. 임베드할 예시 게임 1종의 확정 — 기준(추천 동선 연결)은 정해졌고 구체 게임은 미정.
  2. 모달·임베드·추천 카드가 같은 예시 데이터를 재사용하는 일관성 규칙.
  3. design v0.7에 게임 페이지 임베드가 반영돼 있는지 — **미확인**. → 태스크 X7

## 해자 (전략적 심장 — v0는 예고만, 빌드 0)

### COM — 아키타입 커뮤니티
- **정의:** **같은 코어(아키타입)의 사람들이 모이는 커뮤니티** — "너 같은 사람들" 목록, 유저 카운트. 제품의 전략적 해자지만 v0 랜딩에서는 "coming soon" 예고만 한다(실기능 0).
- **PRD 근거:** FR-009 coming soon 목록(① 너 같은 사람들 ② 유저 카운트 ③ 스냅샷 공유) · PRD §4(커뮤니티 = 해자).
- **정해야 할 것:**
  1. "너 같은 사람들"의 매칭 기준 — 코어 기준인가, 코어+보조태그인가. (v0에는 불필요 — 실빌드 전 결정. 지금은 `[미정]`으로만 유지.)
  2. coming soon 예고의 표현 수위 — 기대감은 주되 실기능처럼 오인되지 않게. → X7 관측 후
  3. design v0.7 반영 현황 — **미확인**. → 태스크 X7

### SNP — 스냅샷·공유
- **정의:** 내 취향 아틀라스를 **사진 한 장으로 정적 렌더해 공유**하는 기능(옛 "정체성 카드"의 재정의). v0는 공유 버튼 자리에 coming soon 표식만. 다음 실물 단계 = $0 공유 게이트(빌드 없이 공유 수요를 검증하는 실험).
- **PRD 근거:** Key Entity "아틀라스 스냅샷" · PRD §6.5($0 게이트) · 헌법 III(실배관 0줄).
- **정해야 할 것:**
  1. $0 공유 게이트의 설계 — 무엇을(스냅샷 시안), 몇 명에게, 어떤 채널로, 통과 기준은. (빌드 전 필수 관문.) → 태스크 M5
  2. 스냅샷 한 장에 담길 최소 정보 구성. → 태스크 M5
  3. design v0.7 반영 현황 — **미확인**. → 태스크 X7

## 시스템 · 수익

### UXS — UI/UX 시스템
- **정의:** 모든 화면에 공통으로 걸리는 경험 규칙 — ① 모든 데이터에 "예시/데모" 정직 표식 ② 아키타입 4분면을 동등한 톤으로(어느 쪽도 우열·결핍 없이, 탐험·개척 감정축) ③ 반응형 ④ 카피는 한국어 주 + 영문 포인트. **경계:** 이 도메인은 경험 요구(WHAT)만 말한다 — 레이아웃·비주얼·타이포(HOW)는 design 레포 소유.
- **PRD 근거:** FR-002 · FR-012 · FR-013 · clarify 카피 규칙.
- **정해야 할 것:**
  1. design v0.7의 가드 준수 현황 — **미점검**. → 태스크 X8
  2. 위반 발견 시 처리 절차(라운드 안건화 기준). → X8 결과 후

### REV — 수익
- **정의:** 유료 구독(Pro)의 가격과 손익 구조 — 무엇이 무료이고 무엇이 Pro인가.
- **PRD 근거:** PRD v0.5 부록 B(수익 가설 — 참고·미확정).
- **정해야 할 것:**
  1. Pro 월 가격 `[미정]` — 착수 전 손익 계산 필요. → 태스크 B1
  2. 무료/Pro 경계선(어떤 기능이 유료 벽 뒤로 가는가). → B1 이후

## 운영 규칙 요약 (이 원장을 쓰는 법)

- 도메인마다 **정의(저맥락) → 정해야 할 것 → 태스크** 순. 결정이 나면 "정해야 할 것"에서 지우고 정의에 흡수.
- 빈 칸(`[미채움]`·미확인)은 숨기지 않는다 — 그게 다음 태스크다 (점진 채움).
- UI/UX 리트머스: FR·clarify 근거를 못 다는 문장은 이 레포 소관이 아니다 (design 몫 또는 새 라운드 안건).
